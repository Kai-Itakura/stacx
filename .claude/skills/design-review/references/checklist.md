# レビュー観点と既知の罠

`review.mjs` の出力を解釈するための資料。ここに載っているのは**このリポジトリで実際に不具合を見つけた観点**と、**一度間違えた分析**である。

## 目次

1. 横方向の溢れ（2 つの症状に分岐する）
2. `input[type="date"]` と WebKit — 一度間違えた分析
3. `field-sizing-content` が `rows` を無効化する
4. タップ領域の基準
5. 仕様との突き合わせ
6. 報告の作法

## 1. 横方向の溢れ（2 つの症状に分岐する）

### 機序

`components/ui/button.tsx` の `Button` は **`shrink-0`** を持つ。そのため `<header className="flex items-center justify-between">` の行で幅が不足したとき、**ボタンは縮まず、行内で唯一縮める `h1` が犠牲になる**。

ここでタイトルの言語によって症状が変わる。

| タイトル | 折り返せるか | 症状 |
|---|---|---|
| `StacX`（ラテン文字） | 改行機会が無いので不可 | h1 は潰れず、**行がビューポートを溢れる → 横スクロール** |
| `プロジェクト`（日本語） | 任意の文字で可 | **h1 が先に潰れて縦積みになる**。ページは溢れない |

### なぜ `scrollWidth` だけでは不十分か

後者は `scrollWidth == clientWidth` のままなので、「横スクロールが出ないこと」を受け入れ条件にすると**表示が壊れたまま green で通る**。実測例:

| viewport | `/` | `/memos` | `/projects` |
|---|---|---|---|
| 390px | 横スクロール +30px | OK | h1 が 3 行（幅 51px） |
| 375px | +44px | OK | h1 が 6 行（幅 36px） |
| 320px | +99px | h1 が 4 行 | h1 が 6 行 + 溢れ +16px |

**折り返し行数と溢れ px の両方を見る。** `review.mjs` は両方出す。

### 対処の方向

- ナビをボトムタブ等へ移し、ヘッダーの横並び要素を減らす（→ issue #58）
- 応急処置の `overflow-x: hidden` は**はみ出し自体を消さない**（操作できないボタンが残る）ので、原因側を直す

## 2. `input[type="date"]` と WebKit — 一度間違えた分析

**ここが最も間違えやすい。** 実際に一度誤った分析を issue に書いて訂正した。

### 誤り

> グリッドアイテムに `min-w-0` が無いためトラックが縮まない。`min-w-0` を付ければ直る。

**これは誤り。** `components/ui/input.tsx` の `Input` は既に **`w-full min-w-0`** を持っている。`min-w-0` を足しても何も変わらない。

### 正しい機序

因果は逆で、**`min-w-0` があるからボックスが固有幅より狭く潰れている**。実測（Chromium）:

| viewport | `input[type=date]` の実幅 | min-content 幅 | 差 |
|---|---|---|---|
| 390px | 165px | **174px** | −9px |
| 375px | 158px | 174px | −16px |
| 320px | 130px | 174px | −44px |

どの幅でも固有幅を下回っている。この状態でエンジンの挙動が分かれる。

- **Chromium** — 内部の日付表示を圧縮して収める → 見た目は破綻しない
- **WebKit（iOS Safari）** — UA コントロールを圧縮しない → **中身が枠を越えて隣の欄に被る**

つまり **Chromium で「再現しない」は「問題がない」ではない**。`review.mjs` の `squeezed` 検出（固有幅より狭い入力）が出たら、実機で崩れている可能性を疑う。

### 対処の方向

- モバイルは縦積み（`grid-cols-1 sm:grid-cols-2`）にして、固有幅を上回る幅を与える（390px で約 342px 確保 > 174px）
- `min-w-[174px]` のような下限だけを付けると、狭い幅でトラックが縮めず**横スクロールに転化する**。縦積みと併用が前提
- **検証は実機 iOS Safari か WebKit で行う。** Chromium only の確認は検証にならない

## 3. `field-sizing-content` が `rows` を無効化する

`components/ui/textarea.tsx` の shadcn 由来クラスに **`field-sizing-content min-h-16`** が含まれる。この場合 textarea は内容に応じてサイズが決まるため、**`rows={8}` は効かない**。空の状態では `min-h-16`（64px）に縮む。

実測: 画面1 の textarea は SP 342×**64**px / PC 624×**64**px。`rows={8}` が指定されているにもかかわらず 64px。

`docs/04-screens.md` の画面1 要件は「**大きなテキストエリアが画面中央にあり**」なので、これは仕様との乖離である。フォーム下の未使用領域も **49%** あり、最重要画面が画面上部の細い帯になっている。

`review.mjs` は textarea の実寸と `rows` 属性、未使用領域の割合を出す。**`rows` の値と実際の高さが食い違っていたらこの罠**。

## 4. タップ領域の基準

閾値を混同しないこと。「44px 未満は違反」と書くと不正確になる。

| 基準 | 閾値 | レベル |
|---|---|---|
| WCAG 2.5.8 Target Size (Minimum) | 24×24 CSS px | **AA** |
| WCAG 2.5.5 Target Size (Enhanced) | 44×44 CSS px | AAA |
| iOS HIG | 44×44 pt | 推奨 |

画面1（SP）の実測では 10 件が 44px 未満だが、**すべて 24px は超えているため AA は充足**している（保存 50×32、追加 48×28、タグ chip 30px、テーマ切替 32×32）。この場合「AA 違反」ではなく「**AAA / iOS HIG の 44px を下回る**」が正しい表現。

### ただし本物の AA 違反もある

プロジェクトフォーム（`/projects/:id`, `/projects/new`）の**技術スタック chip の削除ボタン `×` は 7×20px** で、幅・高さともに 24px を下回る＝**WCAG 2.5.8 AA 違反**。7px 幅は指では実質押せない。`project-form.tsx` の `aria-label={`${t} を削除`}` が付いた `<button>` が該当する。

`review.mjs` は 24px 未満を分けて数え、**該当要素のラベルとサイズまで出力する**（件数だけでは直せないため）。「44px 未満が N 件」で止めず、AA 違反があるかを必ず確認する。

## 5. 仕様との突き合わせ

`docs/04-screens.md` が 4 画面の要件を定義している。レイアウトが崩れていなくても、**仕様と乖離していれば指摘対象**。

確認すべき点の例:

- **画面1（`/`）** — 大きなテキストエリアが中央 / 開いた瞬間にフォーカス / ヒント表示 / プロジェクトは進行中が既定 / タグは chip / `Cmd+Enter` 保存
  - なお**メモ一覧は画面1 に出さない**方針（判断と折衷案は issue #58 のコメントに記録済み）。一覧は画面3 の責務
- **画面2（`/projects`）** — カード形式・進行中をハイライト
- **画面3（`/memos`）** — タイムライン、プロジェクト/タグでフィルタ、全文検索、「STAR 化する」
- **画面4（`/resume`）** — 未実装

未実装のものを「欠陥」として並べない。**実装済み画面の要件との差分**に絞る（例: 画面1 のテキストエリアが 64px）。

## 6. 報告の作法

- **再現しなかったことを省略しない。** 実機で崩れているのに Chromium で再現しない場合、「問題なし」ではなく「WebKit 固有の可能性が高い」が結論。黙って省くと検証されないまま閉じられる。
- **実測と推定を書き分ける。** 「min-content 幅 174px（実測）」と「WebKit では圧縮されない（推定）」を混ぜない。
- **既存 issue の分析が誤っていたら訂正を明記する。** 誤った修正方針が残っていると、その通りに直しても直らない（§2 が実例）。
- **受け入れ条件を症状ごとに書く。** 「横スクロールが出ない」だけでは §1 後者を取りこぼす。
