# STAR を唯一の記録単位にし、Memo を廃止する

記録の単位を Memo から STAR に移し、Memo は廃止する。

これまでは Memo（学び・成果）が最上位の単位で、STAR はそれを後から昇華した 0..1 の付属物だった。
この形では、問題が起きている最中の記録が扱えない。困っている最中の記録は学びでも成果でもなく
Memo の定義に合わないうえ、途中経過を何件か書くと 1 Memo : 1 STAR の制約でどれに STAR を
付けるか決まらない。問題を書くなら Situation と Task はその時点で決まっているので、最初から
STAR として書く。

STAR は S/T/A/R の 4 項目を持ち、少なくとも 1 項目が書かれていれば残りは空のまま保存できる。状態の列は持たず、
4 項目がすべて埋まっていれば「完成」、S/T のどちらかがあり A/R がどちらも空なら「未解決の問題」と
導出する。解決までの試行錯誤は `stars.notes` の 1 列に自由記述で残す。

## Considered Options

- **Memo を STAR に属する時刻付きの書き留め（0..n）として残す**: 試行錯誤を時系列で残せ、
  1 件ごとに編集・削除できる。ただし Memo に残る用途はこれだけだった（問題の書き殴りは
  Situation に書けばよく、STAR に属さない単発の雑記は STAR 中心にした時点で置き場所が無い）。
  この用途のためにテーブル・外部キー・API・時系列 UI・テストを持つ対価に見合わない。
- **Memo を最上位に残し、「未解決」を `status` の第 3 値にする**: 既存構造の延長で済む。ただし
  途中経過の問題（1 Memo : 1 STAR）は解けず、状態が増えると経歴書出力の条件が複雑になる。
- **Memo と STAR の間に Story を置き、Story から STAR に昇華する**: S/T は問題が起きた時点で
  決まっているので、昇華の手間が増えるだけになる。
- **STAR を唯一の単位にし、試行錯誤は `notes` に持つ（採用）**: 単位が 1 つになり、
  「完成」「未解決」は 4 項目から導出できる。`notes` 1 列でも、Action を作業ログで汚さずに
  最初から要約として保つ、という肝心の価値は確保できる。

## Consequences

- 「完成」「未解決の問題」は列ではなく 4 項目から導出する。経歴書出力の対象は完成した STAR だけ。
- Project を削除すると配下の STAR が連鎖削除される（ADR 0005 の対象が Memo から STAR に移る）。
- 技術選定の理由も STAR として書く（ADR 0007 の経路が変わる）。
- 既存データは Expand / Contract の 2 段階で移行する。まず `stars` / `star_tags` を作って写し、
  古いテーブルは残す。production で移行結果を確かめてから、別のマイグレーションで古いテーブルを消す。
  D1 は取り消せないため、写し間違いがあっても元データから写し直せる状態を保つ。
- STAR の id には元の Memo の id を流用する。STAR 化済みの Memo は本文を `notes` へ入れる。
  未 STAR 化の Memo は本文を `result` へ入れる。`situation` に入れると全件が「未解決の問題」として
  並んでしまうため。Memo は学び・成果を書く単位だったので、4 項目のうちでは Result に最も近い。
- `notes` は 1 列の自由記述で、1 件ごとの時刻や削除は構造として持たない。必要になったら
  STAR の子テーブルとして足せる（既存データの移行は要らない）。
