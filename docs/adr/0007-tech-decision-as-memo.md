# 技術選定理由は専用テーブルを持たず、Memo として記録する

技術選定の理由（なぜその技術を選んだか / トレードオフ・US-06）は、`tech_decisions` のような
専用テーブルを設けず、**通常の Memo として本文に記録する**。分類はタグ（例: `技術選定`）で行い、
経歴書に載せたいものは STAR ログへ昇華させて出力する。

記録から出力までの経路は既存の仕組みだけで完結する。

    Memo（本文に理由・トレードオフ / タグ「技術選定」）
      → STAR ログ（経歴書に載せるものだけ）
      → 経歴書出力（プロジェクト・タグ・期間で絞り込み）

## Considered Options

- **専用テーブル `tech_decisions` を作る（当初の想定）**: 技術名・理由・トレードオフを列に分けられ、
  構造化された出力ができる。ただし**技術選定は毎回発生するものではない**（参画するすべての
  プロジェクトで自分が選定者とは限らない）。発生したときだけ書けばよい情報のために専用の
  テーブル・ドメイン・ルート・UI を持つのは、得られる構造化に対してコストが見合わない。
  さらに「学びの記録」が Memo と tech_decisions の 2 系統に割れ、一覧・全文検索・経歴書生成の
  各所で両方を扱う必要が生じて複雑さが波及する。
- **Memo として記録する（採用）**: `memos.body` は自由記述で、`project_id` による紐付けも
  タグ付けも既にある。タグは第一級エンティティで絞り込み軸として設計済みなので、
  経歴書の「含める要素」の切り分けもタグで表現できる。新しい概念を増やさずに US-06 を満たせる。
- **Project に紐付けた専用テーブル**: 「この PJ で Go を選んだ理由」という粒度は経歴書の
  プロジェクト経歴に直結するが、上と同じ「発生頻度に対して重い」問題を抱える。

## Consequences

- **技術選定理由の検索・絞り込みはタグに依存する。** 運用として `技術選定` のようなタグを
  付けて記録する。タグは明示作成のみ（暗黙作成しない）なので、初回はタグを作る手間がかかる。
- **技術名での構造化された絞り込みはできない。** 経歴書のフィルタ軸はプロジェクト・タグ・期間で、
  技術名で切りたい場合は技術名のタグを作って対応する。`projects.tech_stack` は表示専用で
  絞り込み軸にしない既存方針と整合する。
- **経歴書へ出すものは STAR 化する。** STAR ログを持たない Memo は経歴書に出ない。
  技術選定メモも、経歴書に載せたいなら STAR エディタで昇華させる。
- 将来、技術選定の記録量が増えて構造化された出力（技術ごとの一覧など）が必要になったら、
  そのときに専用テーブルへ切り出す。Memo に蓄積されたデータは本文なので移行時は手作業になる。
