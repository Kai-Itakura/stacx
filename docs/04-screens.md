# 04. 主要画面の仕様

StacX は 4 つの主要画面で構成されます。これに加えて、下記「補助画面」があります。

> 実装状況: 画面 1〜3 は実装済み。**画面 4（レジュメ生成）は未実装**で、そこは仕様（作るべきもの）の記述です。
> 実装済みの画面についても、本ドキュメントに書かれた UI 要件がすべて揃っているとは限りません。

---

## 画面 1: 書く（最重要）

### 目的
業務中に問題が起きた瞬間や成果が出た瞬間に、思考を妨げずに STAR として書き留める。あわせて、いま抱えている未解決の問題を見つけ直せるようにする。

### URL
`/` （ログイン直後のホーム）

### UI 要件

- 上に「未解決の問題」の一覧、下に Composer
- Composer は既定で Textarea 1 つ（= Situation）に Project・タグのチップ。「詳しく書く」で T/A/R を開く
  - ページを開いた瞬間に Situation にフォーカスが当たる
  - S/T/A/R のうち少なくとも 1 項目を書けば保存できる
- 入力中に以下のヒントがサジェスト表示される（控えめに）
  - 「数値で表せる成果はある？（例: LCP 2.5s → 1.2s）」
  - 「なぜその技術を選んだ？」
  - 「チームへの貢献はあった？」
- プロジェクトセレクタはデフォルトで「現在のプロジェクト」が選択済み
- タグはチップ形式で選択（技術チャレンジ / トラブル / チーム改善 等）
- Enter 1 回で改行、`Cmd+Enter` で保存

### 入力項目

| 項目 | 必須 | 備考 |
|---|---|---|
| Situation / Task / Action / Result | △ | 少なくとも 1 項目。既定では Situation だけ見える |
| プロジェクト | ◎ | デフォルトで現在進行中。作成後は変更できない |
| タグ | △ | 複数選択可 |

### データの紐付け
- `stars` テーブルにレコード作成
- `project_id` でプロジェクトに紐づく
- `tags` は中間テーブル `star_tags` 経由
- 技術は STAR に紐づけない。技術スタックは Project の属性で、STAR 単位の技術紐付けは Phase 1 では持たない（`CONTEXT.md`）

## 画面 2: プロジェクト＆コンテキスト管理画面

### 目的
プロジェクトの基本情報・技術スタックを登録し、日々の STAR が自動的に紐づくようにする。

### URL
`/projects`, `/projects/:id`, `/projects/new`

### UI 要件

- プロジェクト一覧（カード形式、現在進行中をハイライト）
- 新規作成・編集フォーム

### 入力項目

| 項目 | 必須 | 備考 |
|---|---|---|
| プロジェクト名 | ◎ | |
| 期間（開始日 / 終了日） | ◎ | 終了日は空で「進行中」 |
| 概要 | ○ | プロジェクトの背景・目的 |
| チーム規模 | ○ | 数値 |
| 自分の役割 | ○ | リード / メンバー / etc |
| 使用技術スタック | ◎ | タグ的に複数登録 |
| 業務形態 | ○ | SES / 受託 / etc |

## 画面 3: STAR 一覧・詳細

### 目的
書き留めた STAR を見返し、未解決の問題に行動と結果を足して完成させる。面接・経歴書でそのまま使える形にする。

### URL
`/stars`（一覧）, `/stars/:id`（詳細。編集と削除を兼ねる）

### UI 要件

- 一覧
  - STAR が新しい順に並ぶ
  - すべて / 未解決 / 完成 を切り替える
  - 各 STAR に状態（`CONTEXT.md` の 完成 / 未解決の問題 / 解決中 / 背景未記入）を表示する
- 詳細
  - S/T/A/R の 4 フォーム、プロパティ（Project / タグ）、作業ログ（`notes`）を 1 画面で編集する
  - S/T/A/R の保存は 4 項目の置き換え。空にした項目は空として保存される
  - 作業ログには「追記」ボタンを置く。押すと `09/19 14:30` の行（ブラウザのローカル時刻）を前置して末尾に足す
  - Project は表示のみで変更できない
  - 入力アシスト
    - 「Situation: どんな状況でしたか？」のような問いかけ
    - 数値入力欄をハイライト

### データ構造
- `stars` テーブルに保存。状態は持たず、4 項目から導出する（ADR 0009）
- **技術選定の理由（US-06）に専用テーブルは持たない。** 通常の STAR として記録し、
  タグ（例: `技術選定`）で分類する（ADR 0007）

## 画面 4: レジュメジェネレーター＆プレビュー画面

### 目的
蓄積されたプロジェクトと完成した STAR（技術選定理由を含む）を統合し、Markdown 形式の職務経歴書として出力する。

### URL
`/resume`

### UI 要件

- 左ペイン: 抽出フィルタ
  - プロジェクト（複数選択）
  - 技術タグ（例: Go, Next.js のみアピールしたい場合）
  - 期間
  - 含める要素（プロジェクト概要 / STAR）
    - 技術選定理由などの切り分けはタグで行う（ADR 0007）
- 右ペイン: Markdown プレビュー（リアルタイム反映）
- 上部: 出力ボタン（クリップボードコピー、ファイルダウンロード）

### 出力フォーマット例

    # 職務経歴書

    ## プロジェクト経歴

    ### 〇〇システム開発（2024/01 - 2024/12）
    - 役割: バックエンドリード（チーム 5 名）
    - 概要: ...
    - 技術スタック: Go, PostgreSQL, AWS

    #### 主要な成果
    - **API レスポンス時間を 40% 改善**
      - 状況: 同時接続数の増加によりレスポンスが劣化
      - 課題: p99 を 500ms 以下に維持する必要があった
      - 行動: クエリ最適化と Redis キャッシュ層を導入
      - 結果: p99 を 280ms まで改善し、SLO を維持

    #### 技術選定
    - **sqlc を採用**
      - 理由: 型安全性と SQL の表現力を両立
      - トレードオフ: 動的クエリは別途実装が必要だが、StacX 規模では問題なし

## 補助画面: タグ管理

### 目的
STAR に付けるタグ（`tags`）を一覧・作成・削除する。STAR 入力中のインライン作成だけだと、綴り違いのタグが増えても整理できないため。

### URL
`/tags`

### 備考
タグは「STAR の性質」の分類軸であり、プロジェクトの `tech_stack`（使用技術）とは別物。
レジュメの技術フィルタ（US-09）は `tech_stack` を見る。
